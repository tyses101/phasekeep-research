  What I saw: my first amplification search (a 2 % step search with local refinement, modelled on what I had read of V1.0's procedure) reported V1.0's N = 1 run counts as "up to 3.4 % off"

  What it was: my own search procedure, not V1.0.  The predicate "some threshold meets both exact tails at R runs" is a sawtooth in R (feasible counts are not an interval),
  so a stepped search lands on a feasible count anywhere above the true minimum.  I had compared V1.0 against that stepped result and called the difference V1.0's error.

Correction: the script now computes the TRUE minimum run count (for each threshold c the feasible R form an interval [R1(c), R2(c)]; the smallest feasible c gives the minimum;
  both ends are found by bisection on exact incomplete-beta tails) and confirms it by brute force (G3): the first feasible count scanning from R = 1 equals the search result in the
  three rows small enough to scan (d = 0.1, eps = 1e-4, 1e-3, 1e-2), and in all nine rows with eps > 0 nothing in the 300 counts below the minimum is feasible while the minimum is.
